# 학습·검증·커밋 규칙

## 준비 단계

JDK 21, Maven Wrapper, JUnit Jupiter, Compiler·Surefire·JAR 설정을 추가한다. 빌드 환경 테스트로 실행 JDK의 컴파일러 존재를 확인하고 clean verify로 JAR까지 생성한다. 환경 구성만 완료한 커밋에 learn/step-00 태그를 붙인다. 현재 문서 커밋을 환경 구현 완료 태그로 표시하지 않는다.

## 각 단계의 작업

1. 이전 완료 태그에서 시작해 이전 서버의 문제를 재현한다.
2. 가장 작은 수정으로 해결해 보고, 책임 분리에 필요한 실제 변경 비용·테스트 격리·자원 소유권을 기록한다.
3. 대응 Tomcat 10.1.34 소스에서 클래스뿐 아니라 메서드·상태·오류·종료를 확인한다. 단계 계획에 조사 근거와 차이 표를 보완한다.
4. 테스트를 먼저 작성해 실패 원인을 확인한 후 구현한다. 기존 테스트와 외부 동작을 유지한다.
5. 관련 테스트·전체 clean verify·실제 HTTP 요청을 실행한다.
6. 해당 단계 학습 문서와 현재 상태·제약을 갱신한 뒤 완료 커밋·태그를 남긴다.

핵심 동작의 근거가 충돌하거나 불명확하면 조사 항목으로 남기고 구현 준비 완료로 표시하지 않는다.

## 테스트 규칙

- 모든 테스트 메서드의 첫 테스트 애너테이션 바로 위에 한국어 주석으로 입력·상황과 실제 assertion의 기대 결과를 쓴다. 매개변수화 테스트도 같다.
- 정상·오류·경계·자원 정리·오류 후 다음 요청을 변경 동작에 맞게 확인한다. 프로젝트 정책과 Tomcat 대응 동작을 구별한다.
- 네트워크·동시성 테스트는 임의 포트, 유한 대기, latch·Future 등 명시적 동기화, 확실한 close와 executor 종료를 사용한다.
- 상태 코드만 검사하지 않고 필요한 경우 본문·바이트 길이·호출 횟수·종료 순서·자원 반환도 확인한다.
- 실행하지 못한 검증은 이유와 남은 작업을 기록한다. 예상 결과를 실제 통과 결과로 적지 않는다.

## 학습 문서 형식

구현 시 doc/01-socket/부터 doc/07-embedded/까지 단계별 문서를 만든다. 이전 한계 → 최소 해결 → 책임 분리 이유 → 변경 전후 흐름 → 실행·테스트 → 실제 Tomcat 차이 → 다음 문제 순서로 쓴다.

실행 증거에는 날짜, 커밋, 환경, 명령, 실제 결과, 검증 범위와 제약을 포함한다. 과거 날짜와 결과를 보존한다. 현재 상태는 overview에, 현재 제약은 reference의 구현 상태 문서에 누적한다.

## 완료 커밋과 태그

| 범위 | 완료 커밋 | 태그 |
|---|---|---|
| 준비 | chore(step-00): 실행 환경 구성 | learn/step-00 |
| 1~7 | feat(step-01): ... ~ feat(step-07): ... | learn/step-01 ~ learn/step-07 |

단계 안의 작업 커밋은 여러 개일 수 있다. 단계 완료 커밋은 코드·테스트·문서가 함께 빌드되는 경계이며, 검증 후에만 태그를 붙인다. 공개한 태그를 이동하지 않는다. 수정 시 새 커밋과 실행 기록을 남긴다.

완주 때 0~7태그를 별도 작업 폴더에서 체크아웃해 각 clean verify와 기록된 실행 방법을 확인한다. README의 태그 사용 예제는 실제 생성된 태그와 예정 태그를 구별한다.
