# 1단계 · 요청 하나를 처리하는 서버

초기 계획 작성 당시 상태는 예정이었다. 2026-11-05 사용자 요청으로 구현·검증했으며 실제 결과는 [1단계 학습·실행 기록](../01-socket/01-endpoint.md)을 따른다. 아래 예정 흐름·완료 기준은 원래 계획으로 보존한다. 기준 Tomcat 태그는 10.1.34다.

## 2026-11-05 구현 착수 조사·결정

사용자가 1단계 구현을 요청했다. 기존 단일 Endpoint 설계를 유지한다. NIO·작업자 분리는 각각 설명 범위·6단계이므로 이번에 도입하지 않는다.

- [Acceptor.run/stopMillis](https://github.com/apache/tomcat/blob/10.1.34/java/org/apache/tomcat/util/net/Acceptor.java#L63): 연결 수 제한 대기 → serverSocketAccept → 종료·pause 재확인 → setSocketOptions. 설정 실패는 closeSocket, 종료 중 수락한 연결은 destroySocket으로 정리한다. 수락 예외는 연결 수를 복구하고 running이면 지연 후 기록한다. NEW/RUNNING/PAUSED/ENDED와 stopCalled·stopLatch를 구별한다.
- [NioEndpoint.setSocketOptions/destroySocket](https://github.com/apache/tomcat/blob/10.1.34/java/org/apache/tomcat/util/net/NioEndpoint.java#L419): wrapper를 connections에 등록하고 non-blocking·timeout을 설정한 뒤 Poller로 넘긴다. wrapper 생성 이전 실패는 원시 소켓을 정리한다. destroySocket은 연결 수를 줄이고 채널을 닫는다.
- [AbstractEndpoint.pause/stop/destroy](https://github.com/apache/tomcat/blob/10.1.34/java/org/apache/tomcat/util/net/AbstractEndpoint.java#L1321), [NioEndpoint.stopInternal/unbind](https://github.com/apache/tomcat/blob/10.1.34/java/org/apache/tomcat/util/net/NioEndpoint.java#L273): pause는 unlockAccept의 자체 연결로 accept를 깨운다. stopInternal은 running 해제·Acceptor 대기·Poller 종료·Executor 종료를 수행한다. 수신 소켓 해제는 bind 상태에 따른 unbind에서 수행한다. 모든 stop이 즉시 포트를 반환한다고 일반화하지 않는다.

프로젝트 선택: 생성자는 wildcard 주소에 바인딩하고 0은 임의 포트다. serve는 한 번만 호출하며 종료 후 재시작하지 않는다. close 전 serve는 정상 반환한다. 수락 연결 등록과 close는 같은 잠금으로 보호하고, 잠금 밖에서 읽는다. 종료가 먼저면 새 연결을 즉시 닫는다. 연결 IOException은 해당 연결만 정리하고 계속하며 수락 IOException은 종료 중이 아니면 호출자에게 전파하고 서버도 정리한다. 응답 본문은 `안녕하세요, simple-tomcat!\n`, UTF-8 바이트 길이와 Connection: close를 전송한다. 헤더는 저장 없이 CRLFCRLF만 찾고 EOF 미완성이면 무응답이다. 헤더 크기·읽기 시간 제한·HTTP 문법 검사는 이번에 도입하지 않는다.

변경 파일: `src/main/java/simpletomcat/util/net/Endpoint.java`, 같은 패키지의 `EndpointTest.java`, `doc/01-socket/01-endpoint.md`, README·문서 목차·진행 기록·구현 제약. 기존 Maven 설정은 유지한다.

실행 순서: 테스트 작성 → 미구현 실패 확인 → 최소 구현 → 관련 테스트 → 전체 clean verify → 실제 HTTP 두 요청·프로세스 종료·포트 반환 → 문서·차이 갱신 → 함께 커밋·learn/step-01. 테스트는 실제 임의 포트·유한 소켓/Future 대기·시작 latch·스레드 스택 기반 대기 상태 확인으로 동기화한다. 연결 등록과 종료 경합은 공통 latch를 쓰는 반복 실험 및 잠금 순서 검토로 확인하며 모든 스케줄을 증명한다고 표현하지 않는다.

## 이전 문제와 최소 해결

0단계에는 빌드 환경만 있다. TCP 연결을 수락한 뒤 언제 응답하고 무엇을 닫아야 두 번째 요청을 받을 수 있을까? 먼저 한 클래스에서 accept·헤더 끝 읽기·고정 응답을 구현한다. 응답 후 서버까지 닫는 경우와 요청 연결만 닫는 경우를 비교한다.

## 익힐 개념과 인터페이스

TCP는 바이트 스트림이며 read 경계와 상대의 write 경계가 일치하지 않는다. 헤더 끝 CRLF 두 번, 응답의 바이트 길이, EOF, 연결·서버 수명과 자원 소유권을 익힌다.

예정 구현은 `simpletomcat.util.net.Endpoint(int port)`의 `getPort()`, `serve()`, `close()`다. 생성 시 바인딩하고 0이면 임시 포트를 사용한다. serve를 실행하는 스레드와 종료를 요청하는 스레드를 구별한다.

## Tomcat 구현 근거와 핵심 대응

[Acceptor.run](https://github.com/apache/tomcat/blob/10.1.34/java/org/apache/tomcat/util/net/Acceptor.java)은 연결을 수락해 Endpoint로 인계하고 실패한 연결을 정리한다. HTTP 해석은 하지 않는다.

| 핵심 동작 | Tomcat 동작 | 프로젝트 예정 흐름 | 테스트 |
|---|---|---|---|
| 연결 수락·소유권 | Acceptor 수락·인계, Endpoint 측 연결 정리 | accept → 현재 연결 등록 → 헤더 읽기 → 고정 응답 → 연결 close → 다음 accept | 두 연결·EOF·종료·포트 반환 |

## 구현 작업과 완료 기준

1. EndpointTest에 아래 시나리오를 작성해 미구현으로 실패함을 확인한다.
2. Endpoint 한 클래스와 main을 구현한다. 아직 Processor·Adapter를 만들지 않는다.
3. close가 수신 소켓과 읽기 중 연결을 닫아 대기를 해제하게 한다. 등록·종료 경합에서 새 연결을 놓치지 않게 한다.
4. 단계 학습 문서·현재 상태·차이를 갱신하고 전체 검증 후 완료 커밋과 learn/step-01을 남긴다.

- 같은 서버에서 두 요청에 상태 200·고정 본문·올바른 UTF-8 Content-Length를 받는다.
- 분할된 헤더 끝을 완성하기 전에는 응답하지 않고 완성 후 응답한다.
- 헤더 미완성 EOF이면 응답 없이 닫고 다음 연결에 응답한다.
- accept·헤더 읽기 중 close로 작업이 유한 시간 안에 끝난다. 반복 close·포트 재바인딩도 확인한다.

## 실행 계획

구현 후 clean verify를 실행한다. `java -cp target/classes simpletomcat.util.net.Endpoint 18081`을 시작하고 별도 터미널에서 `curl --max-time 3 -i http://localhost:18081/hello`를 두 번 보낸다. Windows에서는 curl.exe를 사용한다. Ctrl+C로 종료한 뒤 포트 반환을 확인한다. 초기 계획 당시에는 실행 결과가 없었다. 이후 실제 검증에서는 포트 0으로 할당된 61351에서 두 HTTP 요청과 종료 후 포트 반환을 확인했다. 날짜·명령·결과·제약은 위 실행 기록 링크에 보존한다.

## 차이와 생략

| 항목 | 실제 Tomcat·근거 | 예정 동작 | 이유 | 영향·제약 | 검증 | 후속 |
|---|---|---|---|---|---|---|
| 책임 | Acceptor와 Processor 분리 | Endpoint에 HTTP 고정 응답 포함 | 분리 전 모델 | 올바른 HTTP인지 검사하지 않음 | 잘못된 요청도 고정 응답 | 2단계에서 해소 |
| EOF·오류 | 파서·상태별 처리 | 미완성 EOF 무응답, 연결 IOException 뒤 다음 연결 | 파서 이전 모델 | 오류 응답 상세 없음 | EOF 뒤 정상 요청 | 2단계 정책으로 교체 |
| 실행 | NIO 기반 인계 | 블로킹 순차 | 연결 수명에 집중 | 느린 연결이 다음 요청 지연 | 읽기 대기·종료 | 동시성은 6단계, NIO는 설명 |
