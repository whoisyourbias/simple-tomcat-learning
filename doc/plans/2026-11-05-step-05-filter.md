# 5단계 · 컨테이너 처리와 애플리케이션 필터

상태는 예정이다. 기준 Tomcat 태그는 10.1.34다.

## 이전 문제와 최소 해결

로그·접근 검사를 서블릿마다 복사하면 변경이 퍼진다. 호출을 함수로 감싸는 최소 해결부터 시작해 여러 앱의 적용 범위, 전후 처리, 다음 호출을 생략하는 경우를 추가한다.

## 개념·인터페이스·작업

4단계 Pipeline에 사용자 Valve를 추가한다. Valve는 다음 호출을 넘길 수 있어야 하고 마지막 기본 Valve는 컨테이너 본래 동작을 수행한다. 실제 Tomcat의 next 연결 방식과 선택한 최소 계약의 차이를 기록한다.

Filter는 init/doFilter/destroy, FilterChain은 doFilter 계약을 갖는다. Context에 필터를 등록하고 WrapperValve가 요청별 ApplicationFilterChain을 구성한다. 최소 범위는 Context 전체 REQUEST 필터의 등록 순서다. 체인의 위치는 요청마다 분리한다.

## Tomcat 구현 근거와 대응

[StandardPipeline.addValve/getFirst](https://github.com/apache/tomcat/blob/10.1.34/java/org/apache/catalina/core/StandardPipeline.java), [StandardWrapperValve.invoke](https://github.com/apache/tomcat/blob/10.1.34/java/org/apache/catalina/core/StandardWrapperValve.java), [ApplicationFilterChain.doFilter/internalDoFilter](https://github.com/apache/tomcat/blob/10.1.34/java/org/apache/catalina/core/ApplicationFilterChain.java)를 대조한다.

| 핵심 동작 | Tomcat 동작 | 프로젝트 예정 흐름 | 테스트 |
|---|---|---|---|
| 컨테이너 체인 | 사용자 Valve·기본 Valve 연결 | Engine Valve → 기본 호출 → 하위 Pipeline | 두 앱 적용 범위 |
| 앱 체인 | WrapperValve가 체인 실행, 마지막에 service | Filter A → B → Servlet → B → A | 순서·중단·예외 복구 |
| 객체·요청 상태 | 필터 객체와 체인 진행 상태 구별 | 앱 필터 재사용, 요청별 체인 | 요청 간 위치 격리·초기화·해제 |

## 완료 테스트·실행

- A 전 → B 전 → Servlet → B 후 → A 후 순서를 정확히 확인한다.
- 중간 필터가 응답을 끝내고 chain을 호출하지 않으면 Servlet 호출이 0회다.
- Engine Valve는 두 앱에, 특정 Context Filter는 해당 앱에만 적용된다.
- 필터·서블릿 예외 후 다음 요청의 체인 위치가 처음부터 시작한다.
- 필터의 초기화·해제 횟수와 실패 초기화 자원 정리를 검증한다.

테스트 실패 → Pipeline 확장 → Filter 계약·등록 → WrapperValve 연결 → clean verify·HTTP → 문서·완료 커밋·learn/step-05 순서다. 예정 실행 클래스는 `simpletomcat.examples.FilterServer`이며 /hello의 호출 추적을 확인한다. 현재 실행 기록은 없다.
